# Understand the Fibey toolbox integration

Model Context Protocol (MCP) provides a common interface for discovering and calling tools. Fibey connects to one Microsoft Foundry Toolbox endpoint; the toolbox routes requests to the configured operational systems.

This keeps backend addresses and credentials out of the prompt. It does not eliminate downstream authentication: each Foundry connection still needs the right credentials and permissions.

## Follow one request

A technician's message passes from the Entra-protected UI through the internal gateway to the hosted agent. The agent loads a relevant skill, checks the tools actually available, and calls the selected operations.

Inventory and network status share the inventory MCP connection and the `inventory-lookup` skill. `get_network_status` fetches only the configured internal dashboard; it is not an arbitrary URL fetcher or a browser-automation tool.

```text
Allowlisted user → UI → internal gateway → Foundry hosted agent
                                           ↓
                                     Foundry Toolbox
                     ┌─────────────────────┼───────────────────┐
                Inventory MCP       Work Orders OpenAPI    Foundry IQ MCP
                     ↓                                      ↓
              internal dashboard                         AI Search
```

## Use the interface the toolbox actually exposes

The sample's toolbox configuration exposes **11 operational tools directly**. Their names and input schemas are available through MCP tool enumeration; the agent does not need a `tool_search` or `call_tool` wrapper to invoke an already-visible tool.

Other toolbox configurations may expose discovery and invocation *meta-tools*: tools that find or call other tools. Fibey's system prompt and all five skills support that interface only when it is actually available. A missing meta-tool is not, by itself, a broken toolbox.

| Available interface | How the agent proceeds after loading a skill |
|---|---|
| Direct operational tools — current deployment | Select a visible tool and invoke its exact name with its advertised input schema |
| `tool_search` and `call_tool` meta-tools | Discover missing capabilities with one combined query and `limit: 10`; invoke returned names through the available wrapper |
| Neither the required operation nor a supported discovery tool | Report the unavailable capability; do not invent tool names or results |

Always follow the advertised schema, not old autogenerated OpenAPI operation names or an assumed unprefixed knowledge tool. Work-order writes may require a `body` wrapper. The deployed knowledge retrieval schema uses a **one-element `query_variants` array**; retain the complete question in that request and use the schema's required element structure. Combine related procedure and safety questions into one retrieval call.

Record the toolbox and hosted-agent versions accepted in your environment. Verify work-order, inventory/status, and knowledge calls, then a combined briefing with citations, streaming, follow-up context, and reset. Enumeration alone is insufficient, and another environment's successful demonstration is not evidence that yours is ready.

## Use the supported hosted integration

`src/fibey/agent/hosted.py` uses `FoundryToolbox` from `agent_framework_foundry_hosting`, then awaits `ResponsesHostServer.run_async()`. The SDK authenticates MCP requests and forwards per-request platform context, including the runtime call ID.

Do not replace it with a custom bearer-only transport or global MCP/Pydantic patches. Those shortcuts can lose platform context or change validation for every tool in the process. History retrieval failures must fail the turn rather than silently discarding the conversation.

The implementation follows the [official Foundry toolbox sample](https://github.com/microsoft-foundry/foundry-samples/tree/main/samples/python/hosted-agents/agent-framework/responses/04-foundry-toolbox):

- `FoundryToolbox` resolves `TOOLBOX_ENDPOINT`, or builds an endpoint from `FOUNDRY_PROJECT_ENDPOINT` and `TOOLBOX_NAME`.
- `FoundryChatClient` uses the selected model; the agent sets `default_options={"store": False}` because hosted conversation history is managed by Foundry.
- `ResponsesHostServer` owns agent/tool lifecycle. The entrypoint also closes the project client, model client, toolbox client, and credential.
- OpenTelemetry is enabled. `ENABLE_SENSITIVE_TELEMETRY=true` explicitly enables sensitive content tracing; the default is off.

The supporting infrastructure provisions ACA Log Analytics, not an Application Insights resource. Verify the hosted project's linked telemetry destination and receipt of a synthetic trace separately; enabled instrumentation is not proof of trace ingestion.

The locked packages include `agent-framework-core`, `agent-framework-foundry`, and `agent-framework-foundry-hosting`. Use `uv sync --frozen`; do not substitute an old hosting version that lacks `FoundryToolbox`.

## Keep skills available

The five bundled skill documents describe inventory lookup, work-order management, knowledge retrieval, work-order preparation, and field briefings. They preserve the demo's instruction-driven routing even when optional published skills are unavailable.

Hosted discovery uses the SDK's MCP skills source on the authenticated toolbox session. Read-only skill loading does not require a host approval round trip, because this demo has no approval UI. That is distinct from enforcing approval on operational writes.

| `SKILLS_SOURCE` | Hosted behavior |
|---|---|
| `auto` | Prefer published versions by name; retain other bundled skills; fall back if discovery fails |
| `file` | Use bundled skills without remote discovery |
| `mcp` | Require published skills; fail clearly if they cannot be loaded |

Local mode still supports the legacy `resources/list` skill adapter as well as bundled files. Use `file` for deterministic local rehearsals. An invalid mode or missing required skill source is an error, not permission to run without the intended instructions.

## Separate the authentication boundaries

The agent's Azure credential authenticates it to Foundry. Foundry connection credentials authenticate the toolbox to the operational services. These are separate boundaries, even though the agent sees one toolbox endpoint.

The setup scripts register only the intended operations. They deliberately do not promise approvals or expose demo-reset controls as tools.

| Capability | Connection and access |
|---|---|
| Inventory and status | Remote MCP connection; `x-api-key` to protected external inventory ACA |
| Work orders | OpenAPI `project_connection` auth; the connection stores an `x-api-key` credential for the `APIKeyHeader` scheme |
| Knowledge retrieval | Knowledge-base MCP connection; project managed identity with Search permissions |
| Dashboard fetch | Inventory service to a fixed internal dashboard URL |

Run `scripts/setup-knowledge-base.ps1` before `scripts/setup-toolbox.ps1`, after deploying the protected services. The toolbox script obtains the live OpenAPI document with the configured key and keeps secrets in Foundry connections rather than the rendered tool definition.

The API versions apply to different endpoints; do not interchange them:

| Endpoint purpose | Configured API version |
|---|---|
| Foundry toolbox MCP | `v1` |
| Hosted agent Responses | `v1` |
| Search index, indexer, datasource, and knowledge-source configuration | `2026-04-01` (GA) |
| Knowledge-base defaults and MCP retrieval | `2026-08-01-preview` |

The preview knowledge-base definition explicitly sets `retrievalReasoningEffort.kind: minimal` and `outputMode: extractiveData`; otherwise MCP retrieval can require an additional model. It also sets default limits of three output documents and 6,000 output tokens. The configured MCP endpoint uses the preview API because the GA MCP version was rejected in this deployment.

## Understand local and legacy modes

`AGENT_MODE=local` runs the agent inside the gateway; `python -m fibey.agent.main` runs it in a terminal. Local toolbox access uses `MCPStreamableHTTPTool` with a developer Azure credential, or the optional legacy toolbox account-key setting. The separate backend API keys still belong in Foundry connections.

The optional `fibey.agent.service` adapter supports `containerapp` gateway mode for local/legacy experiments. It is not deployed by the current `azure.yaml`, and its local development interface must not be presented as the protected production architecture.

Set `TOOLBOX_MCP_URL` to your actual endpoint. The setup script publishes a default version and saves the unversioned consumer endpoint; the current platform contract routes that endpoint to the published default. A version-specific developer URL can be used to test an immutable candidate. Local code appends `api-version=v1` only when it is missing. Do not use a date-based API version for the toolbox itself.

Local mode explicitly enables read-only skill loading for the unattended gateway/CLI and keeps `AgentSession` history between turns. Per-turn credentials and HTTP clients are closed when a turn completes or fails.

## Preserve the streaming contract

Server-sent events (SSE) are small text frames separated by a blank line. The gateway translates Foundry Responses events into `delta`, `activity`, `citation`, `error`, and `done` frames; the UI uses activity events for its tool sidebar.

The gateway validates bounded messages and UUID session IDs, returns `X-Session-Id`, and never logs user message text. A completed response terminates the stream immediately; premature EOF, malformed data, timeouts, and response-level failures produce an error rather than a false success.

`HOSTED_AGENT_ENDPOINT` normally contains the project URL and is combined with `HOSTED_AGENT_NAME`, using `api-version=v1`. `HOSTED_AGENT_RESPONSES_URL` can instead supply an exact HTTPS Responses URL. These are server settings, never browser-supplied upstream addresses.

The platform creates the first hosted compute session. The gateway captures its `x-agent-session-id` response header or response payload's `agent_session_id`, then sends `agent_session_id` in subsequent request bodies alongside `previous_response_id`. The first controls sandbox affinity; the second controls conversation history. Gateway Responses requests use `store: true` for that history, separately from the agent's model-call `store: false` setting.

These mappings are in memory and require one gateway replica. The gateway rejects overlapping turns/reset requests for the same active session. Reset clears local history, the previous-response mapping, and the compute-session mapping so the next turn starts fresh; it does not delete the old remote sandbox. This is not durable storage or per-user session authorization.

## Diagnose by boundary

Start with the failing boundary rather than changing SDK internals. A token problem, a missing Foundry connection, and a malformed tool result need different remedies.

Use synthetic prompts and redacted logs during diagnosis. Avoid enabling sensitive telemetry just to check endpoint availability.

| Symptom | Check |
|---|---|
| UI does not start | Required `GATEWAY_HOST` and exact HTTPS `/api/` URL |
| UI sign-in denied | Entra app redirect URI and allowed user object ID |
| Gateway startup fails | Explicit mode, HTTPS project/Responses URL, timeout configuration |
| Model or toolbox authorization fails | Runtime identity, project permissions, connection scope |
| Inventory/work-orders returns 401/403 | Deployed API key and matching Foundry connection credential |
| OpenAPI reports unknown auth type or missing key | Use `project_connection` and store the credential under the HTTP header name `x-api-key` |
| Knowledge retrieval fails | Search ingestion, MCP API version, project identity roles, and advertised `query_variants` schema |
| Knowledge retrieval requires a model | Verify explicit minimal reasoning/extractive output in the preview knowledge-base definition |
| Multi-tool briefing is rate-limited | Model deployment TPM/RPM allocation and bounded retrieval results |
| UI proxy returns 502 with certificate-chain errors | Trusted CA bundle, SNI, and `proxy_ssl_verify_depth 3`; retain TLS verification |
| `tool_search` or `call_tool` is missing | Check the visible operational tools; the current toolbox exposes them directly |
| Status fails | Inventory's configured internal dashboard URL and reachability |
| Skills unavailable | `SKILLS_SOURCE`, published skill support, bundled files in the image |
| Stream ends early | Terminal failure/timeout; do not suppress history or transport errors |

See [Deployment](deployment.md) for the staged setup and verification sequence.
